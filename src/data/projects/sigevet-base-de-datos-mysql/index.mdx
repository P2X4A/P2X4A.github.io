## Las restricciones por dentro

La tabla `CITA` muestra cómo se combinan los cuatro tipos de restricción. Un veterinario no puede tener dos citas a la misma hora (`UQ_CITA_VETERINARIO_FECHA_HORA`), el estado solo admite cuatro valores y cada llave foránea apunta a su tabla.

```sql
CREATE TABLE CITA (
    id_cita         BIGINT NOT NULL AUTO_INCREMENT,
    fecha_hora      DATETIME NOT NULL,
    motivo          VARCHAR(200),
    estado          VARCHAR(12) NOT NULL DEFAULT 'PROGRAMADA',
    id_mascota      INT NOT NULL,
    id_veterinario  INT NOT NULL,
    id_sede         INT NOT NULL,
    id_servicio     INT NOT NULL,
    CONSTRAINT PK_CITA PRIMARY KEY (id_cita),
    CONSTRAINT UQ_CITA_VETERINARIO_FECHA_HORA UNIQUE (id_veterinario, fecha_hora),
    CONSTRAINT CK_CITA_ESTADO CHECK (estado IN ('PROGRAMADA','ATENDIDA','CANCELADA','NO_ASISTIO')),
    CONSTRAINT FK_CITA_MASCOTA FOREIGN KEY (id_mascota) REFERENCES MASCOTA (id_mascota),
    CONSTRAINT FK_CITA_VETERINARIO FOREIGN KEY (id_veterinario) REFERENCES VETERINARIO (id_empleado),
    CONSTRAINT FK_CITA_SEDE FOREIGN KEY (id_sede) REFERENCES SEDE (id_sede),
    CONSTRAINT FK_CITA_SERVICIO FOREIGN KEY (id_servicio) REFERENCES SERVICIO (id_servicio)
) ENGINE=InnoDB;
```

El fragmento omite los comentarios de columna que sí tiene el script original.

## Reglas que el modelo relacional no expresa

Hay reglas que ni un CHECK ni una llave foránea pueden declarar, porque comparan filas de tablas distintas: que el veterinario de una cita trabaje en la sede de la cita, que un veterinario sea de tipo veterinario, que solo una cita atendida tenga consulta. Se implementaron con disparadores que llaman a procedimientos y que rechazan el dato con `SIGNAL SQLSTATE '45000'` y un código de error propio. En MySQL un disparador cubre un solo evento, así que la lógica compartida vive en los procedimientos y la llaman los disparadores de `INSERT` y de `UPDATE`.

```sql
-- RN-08: el veterinario de una cita debe trabajar en la sede de la cita.
CREATE PROCEDURE PR_VALIDAR_SEDE_VETERINARIO (p_id_veterinario INT, p_id_sede INT)
BEGIN
  DECLARE v_sede INT;
  DECLARE v_mensaje VARCHAR(200);
  SELECT id_sede INTO v_sede FROM EMPLEADO WHERE id_empleado = p_id_veterinario;
  IF v_sede <> p_id_sede THEN
    SET v_mensaje = CONCAT('El veterinario ', p_id_veterinario, ' labora en la sede ', v_sede,
                           ', no en la sede ', p_id_sede, '.');
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = v_mensaje, MYSQL_ERRNO = 20003;
  END IF;
END$$
```

| Código | Qué rechaza | Dónde está |
| :-- | :-- | :-- |
| 20001 | Una fila en `VETERINARIO` cuyo empleado no es de tipo veterinario | Disparadores de `VETERINARIO`, con `PR_VALIDAR_TIPO_EMPLEADO` |
| 20002 | Una fila en `AUXILIAR` cuyo empleado no es de tipo auxiliar | Disparadores de `AUXILIAR`, con `PR_VALIDAR_TIPO_EMPLEADO` |
| 20003 | Una cita con un veterinario que labora en otra sede | Disparadores de `CITA`, con `PR_VALIDAR_SEDE_VETERINARIO` |
| 20004 | Una consulta de una cita que no está atendida | Disparadores de `CONSULTA`, con `PR_VALIDAR_CITA_ATENDIDA` |
| 20005 | Cambiar el tipo de un empleado que ya tiene fila de subtipo | `TRG_EMPLEADO_TIPO` |
| 20006 | Sacar del estado atendida a una cita que ya tiene consulta | `TRG_CITA_UPD` |

## Carga y verificación

El script `cargar_bd.sh` ejecuta todo en el orden que exigen las dependencias: usuarios como root, tablas, índices, programas, datos, vistas, verificación y, al final, los permisos de la aplicación, porque MySQL solo concede permisos de tabla sobre tablas que ya existen. Los programas van antes de los datos porque los disparadores validan cada `INSERT`.

```text
bash vm/scripts/cargar_bd.sh               crea la base y los usuarios y carga todo
bash vm/scripts/cargar_bd.sh --reiniciar   borra la base y la vuelve a cargar
```

- La llave foránea `FK_SEDE_DIRECTOR` es circular (EMPLEADO referencia a SEDE y SEDE a EMPLEADO): las sedes se insertan sin director y el director se asigna con un `UPDATE` cuando ya existen los empleados.
- Para que el usuario dueño cree funciones y disparadores con el registro binario activo hace falta `log_bin_trust_function_creators = 1`; sin eso, el script de programas falla con el error 1419.
- La carga tarda de 1 a 2 segundos, y las 10 pruebas de reglas de negocio (llaves foráneas, CHECK, UNIQUE y disparadores) pasan en OK.
- Los 1,08 MB son datos más índices según `DATA_LENGTH` más `INDEX_LENGTH` en `information_schema.TABLES`; no es el espacio que ocupan los archivos del servidor en el disco.

## Mínimo privilegio

La aplicación nunca entra como administrador. `vetdb` es el dueño del esquema y `vet_app` recibe dos roles.

| Usuario o rol | Privilegios |
| :-- | :-- |
| `vetdb` | Todos los privilegios sobre `sigevet`; solo sobre ese esquema |
| `rol_sigevet_lectura` | `SELECT` y `SHOW VIEW` sobre `sigevet` |
| `rol_sigevet_escritura` | `INSERT` y `UPDATE` sobre 12 tablas; `DELETE` solo en `CLIENTE`, `TELEFONO_CLIENTE`, `INVENTARIO` y `VETERINARIO_ESPECIALIDAD`; `DETALLE_FACTURA` solo con `INSERT` |
| `vet_app` | Los dos roles anteriores, sin `DROP`, `ALTER` ni cambios en los catálogos |

La prueba de privilegios del equipo, ejecutada como `vet_app` en el servidor, confirma lo que debe fallar:

| Intento | Resultado |
| :-- | :-- |
| `DELETE` sobre `MASCOTA` | Error 1142: comando denegado |
| `UPDATE` sobre `SERVICIO` | Error 1142: comando denegado |
| `INSERT` en `ESPECIE` | Error 1142: comando denegado |
| `DROP TABLE` sobre `CITA` | Error 1142: comando denegado |
